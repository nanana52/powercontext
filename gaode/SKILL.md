# 周边去哪儿：基于高德的步行地点推荐

## 目标和边界

- 根据用户给定的**城市、起点经纬度和自然语言需求**，使用高德 MCP Server 查找真实地点，查询从**同一个起点**分别前往各候选地点的**步行路线**，再推荐最多 3 个符合条件的地点。
- 优先满足硬性条件（地点类型、步行时间上限、数量上限），再考虑“优先近一点”、地点特色等偏好。实际步行距离与时间必须来自高德**步行路线规划**，绝不可用直线距离、搜索距离或自估速度代替。
- 任务为多个独立目的地的备选推荐；不要将地点串联成多站路线。只需完成一次“理解需求 → 查询高德 → 筛选推荐 → 解释结果”。
- 运行环境和高德工具由宿主平台提供；不要要求用户提供高德 API Key，不要安装或配置 MCP Server，不需要访问数据库、长期记忆或其他外部服务。

## 1. 理解并记录用户约束

从本轮用户输入和平台提供的任务上下文提取：

| 字段 | 提取规则 |
| --- | --- |
| `city` | 用户明确给出的城市；用于约束地点搜索和核对城市一致性。 |
| `origin` | 平台明确给出的起点坐标，保持原样，使用高德所需的 `经度,纬度` 顺序；**不要**把经纬度反过来。 |
| `category` | 具体地点类型，如咖啡馆、餐厅、公园、书店；不得把其他类型硬凑成符合结果。 |
| `max_minutes` | “步行不超过/以内 N 分钟”表示**实际路线耗时 ≤ N×60 秒**；没有时间限制时不要虚构一个。 |
| `requested_count` | 识别“最多 N 家/个”，如未指定则默认最多 3 个；最终输出数量为 `min(N, 3)`，不可超过。 |
| `preferences` | 如“优先近一点”“适合散步”“安静”“不排队”，只有高德数据确实支持时才将其作为事实性依据。 |

若输入同时包含地铁站名称和**明确起点坐标**，以提供的坐标为出发点，不要用地铁站地理编码替换。无需设备定位或询问用户“你在哪里”。若确实没有任何可用起点坐标、且平台也未给定，才说明无法精确规划步行路线并请求起点，不得编造坐标。

## 2. 使用高德工具搜索真实 POI

1. 优先使用高德 MCP 的 **`maps_around_search`**（周边搜索），将 `keywords` 设为用户要求的类型关键词，将 `location` 设为起点 `经度,纬度`；若工具接受 `radius`，为初次召回设置适度半径（通常 1500–2000 米；时间上限较短时可缩小，查询不足时可扩大）。搜索半径只用于查候选，**不能代替步行时间判断**。
2. 依据实际工具 schema 传参；不要臆造工具参数。如平台提供的是同等语义的高德“周边搜索”工具而名称不同，使用相应工具。`maps_around_search` 不可用时，可尝试高德 **`maps_text_search`**（关键词搜索，以 `city` 限定城市），再使用起点坐标和步行路线核实；不要退化为模型凭记忆编地点。
3. 从工具的 `pois` 或等价结果读取真实 `id`、`name`、`address`、`location`、`type` 等字段。拒绝无有效名称、坐标的条目；确保目标位于用户要求的城市或合理附近范围、类别与需求相符。按照 POI ID 去重，名称和位置高度重复的门店也去重。
4. `address` 不完整时，可调用 **`maps_search_detail`** 或等价详情工具按真实 POI ID 补充；仍未获得地址时标记“地址未核实”，优先选择有可信地址的候选。不要补写看似合理但工具未提供的门牌号。
5. 从候选中选择一批有代表性的真实地点进入路线查询（通常先取 8–12 个，搜索较少时查询全部）。不要仅凭周边搜索返回的“distance”或结果顺序直接选出最终推荐。
6. 搜索无结果时，可以更换一次同义关键词（如“咖啡馆”/“咖啡店”），或在用户允许的空间范围内适度扩大**搜索**半径；不能擅自放宽用户的**步行时间上限**。重试后仍无真实结果，就诚实说明。

## 3. 对每个候选独立规划步行路线（必做）

1. 对每个入选候选分别调用高德 MCP **`maps_direction_walking`**（或同等语义步行路线工具）。每次的 `origin` 都是相同的用户起点 `经度,纬度`，`destination` 使用该真实 POI 的 `location`；不能把上一个地点作为下一个地点的起点。
2. 从真实返回的 `paths` 中读取可用的步行方案。优先选择有效的最短耗时步行路线，记录其 `distance`（通常是米）和 `duration`（通常是秒）。工具数据若在嵌套对象中，按实际字段解析；空对象、错误状态、无 `paths`、非数字或负值均视为路线不可核实。
3. 所有时间硬约束以**原始路线秒数**比较，例如“15 分钟内”严格判断 `duration <= 900`；先比较再展示。最终输出 `距离 = 路线 distance`、`时间 = duration/60` 分钟，可四舍五入到 1 位小数并标注“约”，但不得为了凑整错误地将超时地点归类为达标。
4. **绝对禁止**用 POI 直线距离、高德周边搜索半径、`maps_distance` 的非步行测量、驾车/骑行/公交路线、经验步速推测作为步行数据。路线服务失败的候选不能标为“满足时间限制”。
5. 有步行时间上限时，淘汰所有路线耗时超过上限的候选；没有上限也需提供真实步行路线数据。若某个候选失败，可以尝试查询下一个真实候选；不要伪造距离或时间。

## 4. 结果筛选、排序和说明

1. **先筛选**：地点类型一致，城市/范围合理，真实 POI 可识别，路线可核验，且满足全部硬约束。
2. **再排序**：“优先近一点”时优先按**实际步行耗时升序**，耗时相近时按实际步行距离升序；若用户有其他可验证的偏好，只有在不违背硬约束的情况下才作为次级排序依据。即使没有明确“优先近”，默认也以实际步行时间从短到长排列，方便用户选择。
3. **数量**：最多返回用户要求的数量，且绝不超过 3 个。不得为了凑够 3 个塞入超时、类型不符、无路线或虚构的地点。
4. **推荐理由**：每个候选给出一句基于已核实数据的理由，例如“符合咖啡馆类别，步行约 9.2 分钟，三家中最近”。只有 POI 详情确实提供可信依据时才补充特色。
5. 没有可信依据时，不要断言“安静”“排队少”“营业中”“评分高”“人少”“环境好”“有座位”等；若这些是用户偏好，简短标注“安静程度/排队/营业状态：未核实”，不能虚构。

## 5. 最终回答格式

使用与用户一致的语言，通常为中文；正文短而清楚，推荐用表格（或等价编号列表）：

**从［起点］出发，按实际步行时间排序，推荐以下［地点类型］：**

| 地点 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| ［工具返回的真实 POI 名称］ | ［真实地址］ | ［路线米数］米 | 约［路线秒数÷60］分钟 | ［有依据的一句话］ |

- 仅填入实际查到且符合条件的 0–3 行，不要照搬方括号示例或捏造示例地点。
- 若用户指定 15 分钟上限，可在表前写“以下均满足步行不超过 15 分钟”；只有所有已推荐候选确实逐个通过路线校验时才这么写。
- 候选不足指定数量时，说明“在已查询范围内，仅找到 X 个满足条件的地点”，可建议扩大搜索范围或放宽时间上限；未获用户同意不能擅自放宽。
- 结果为零时，简述是“没有搜索到符合类别的地点”“找到地点但步行时间超限”，还是“高德搜索/路线服务失败”；必要时建议稍后重试。工具失败不等于附近一定没有地点。
- 对未核实的状态或偏好，明确注明“未核实”；如“营业状态、安静程度和排队情况未核实”。避免堆砌冗余解释。

## 6. 输出前的强制自检

- [ ] 每个地点都来自本轮**真实高德 POI 工具返回**，名称、地址没有凭空补写。
- [ ] 每个推荐都有本轮**真实高德步行路线调用**；起点完全相同，终点是对应 POI 坐标。
- [ ] 每个步行距离与时间都来自路线返回值，单位换算正确，没有使用直线距离。
- [ ] 每个地点通过类别、城市、时间上限等全部硬条件；时间在比较原始秒数后再显示。
- [ ] 排序符合用户“优先近一点”等明确偏好；不超过 3 个且不超过用户要求数。
- [ ] 结果不足、无结果、接口报错、来源缺失或未核实的状态均已如实说明。
- [ ] 没有泄露或要求 API Key，没有发明地点、路线、评分、营业状态或额外工具调用。

不要在最终答案中输出虚构的工具调用记录、假设的 JSON 数据或评分说明；平台会自动采集真实的高德工具调用。
